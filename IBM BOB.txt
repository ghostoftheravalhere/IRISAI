8. ARCHITECTURAL BUGS, DEBUGGING, AND IBM BOB CONTRIBUTION

During the real-world development and host-system testing of IRIS AI, several complex runtime and architectural bugs were encountered. IBM Bob was used as an AI engineering companion to analyze log evidence, trace control paths, formulate diagnostic hypotheses, and structure robust architectural fixes under human review.

--------------------------------------------------
A. VOICE SELF-HEARING / AUDIO FEEDBACK BUG
--------------------------------------------------
Problem:
During early two-way voice testing, IRIS listened to its own spoken TTS responses through the host microphone. This caused IRIS's spoken text to be captured by the microphone, transcribed by Faster-Whisper, parsed as a new USER command, and executed recursively. This resulted in infinite feedback loops (e.g., IRIS repeating "I couldn't understand that command").

IBM Bob Debugging Contribution:
IBM Bob assisted in analyzing microphone capture lifecycles, audio buffer draining timings, and Whisper transcription event boundaries. IBM Bob suggested implementing a hardware-level microphone suppression gate during active TTS playback.

Human Team Solution & Integration:
The team implemented a strict half-duplex voice control model: hardware microphone stream suppression while TTS is active, clearing of buffered audio frames upon TTS completion, pre-processing STT suppression gates, and transcript filtering.

--------------------------------------------------
B. FALSE USER TRANSCRIPTS IN COMMAND LOG
--------------------------------------------------
Problem:
An issue was discovered where raw speech transcription events (`TranscriptionCompletedEvent`) were published directly to the WebSocket event bus before passing through the safety and decision validation layers. As a result, recognized audio from IRIS's own TTS output briefly appeared as a USER message in the UI Command Log even if rejected downstream.

IBM Bob Debugging Contribution:
IBM Bob helped trace the event publication pipeline and recommended moving event emission downstream of the safety/decision gate.

Human Team Solution & Integration:
The team restructured the event flow: `STT Audio -> Validation / Safety Gate -> Event Publication`. Raw transcripts are validated before being published to the frontend UI, guaranteeing zero false USER messages.

--------------------------------------------------
C. ORPHANED / DUPLICATE BACKEND PROCESS BUG
--------------------------------------------------
Problem:
On Windows, running Uvicorn with auto-reload enabled spawned multiprocessing child processes (`multiprocessing.spawn`, `spawn_main(parent_pid=...)`, `--multiprocessing-fork`). When the parent backend process exited or restarted, child processes remained orphaned in the background, keeping socket ports bound and running duplicate microphone/camera streams.

IBM Bob Debugging Contribution:
IBM Bob analyzed Windows process evidence (PID parent-child trees, active socket bindings) and identified Uvicorn's reload/multiprocessing fork mechanism as the root cause.

Human Team Solution & Integration:
The team configured production backend execution to run single-process mode (`reload=False`), added explicit SIGTERM/SIGINT teardown handlers in Electron, and implemented process-tree fallback termination (`taskkill /F /T`) to ensure zero orphan processes remain.

--------------------------------------------------
D. APPLICATION SHUTDOWN LIFECYCLE BUG
--------------------------------------------------
Problem:
Closing the Electron application window previously left background Python processes, camera feeds, and microphone audio streams running invisibly in Windows Task Manager.

IBM Bob Debugging Contribution:
IBM Bob assisted in modeling a synchronous, multi-stage application teardown lifecycle contract for Electron's `before-quit` event.

Human Team Solution & Integration:
The team implemented a strict shutdown pipeline: Electron `before-quit` -> Backend API shutdown request -> Camera/MediaPipe stop -> Microphone stream stop -> Python process termination -> Process-tree cleanup. Additionally, safe voice self-close commands (`"Close IRIS"`, `"Exit IRIS"`, `"Quit IRIS"`, `"Close yourself"`, `"Shutdown IRIS"`) were wired directly into this lifecycle.

--------------------------------------------------
E. DESKTOP APPLICATION RESOLUTION BUGS
--------------------------------------------------
Problem:
Initial application launching relied on generic executable execution. This caused runtime failures on Windows:
- Saying `"Open calculator"` attempted to run literal `calculator`, which Windows failed to resolve (Windows error: "Windows cannot find 'calculator'").
- Saying `"Open Microsoft Word"` frequently opened Microsoft Edge or browser web searches instead of desktop Word.

IBM Bob Debugging Contribution:
IBM Bob analyzed Windows application launching mechanisms (App Paths registry, Start Menu shortcuts, URI schemes) and recommended building a dedicated application resolution service.

Human Team Solution & Integration:
The team created `DesktopAppResolver` (`backend/automation/app_resolver.py`), a centralized Windows application registry. It provides strict alias matching for desktop apps (`calc.exe` for Calculator, `Word 2016.lnk` for Word, `Excel.lnk`, `PowerPnt.lnk`, `notepad.exe`), dynamic Start Menu shortcut scanning, and URI protocol activation (`ms-settings:`), completely eliminating browser fallbacks and cross-app collisions.

--------------------------------------------------
F. EYE GAZE CALIBRATION UX BUG
--------------------------------------------------
Problem:
During 9-point eye-gaze calibration, the central instruction modal dialog obscured calibration target points (specifically Point 2 Top-Center, Point 5 Center, and Point 8 Bottom-Center), preventing users from focusing on the target dot.

IBM Bob Debugging Contribution:
IBM Bob assisted in evaluating UI viewport layering, recommending a non-obstructive floating controller layout with dynamic corner positioning.

Human Team Solution & Integration:
The team redesigned the calibration UI: during active sampling, the instruction dialog converts into a compact **Floating Controller Card** anchored at `bottom: 24px, right: 24px` (dynamically shifting to `left: 24px` for bottom targets). Safe target margins (`y: 0.10` to `y: 0.82`) were established, guaranteeing 0 visual overlap across all 9 calibration points.

--------------------------------------------------
G. CURSOR CONTROL STATE/UX BUG
--------------------------------------------------
Problem:
Upon completing 9-point calibration, the UI lacked an explicit control to toggle active gaze cursor control on/off, leaving users uncertain if cursor tracking was active.

IBM Bob Debugging Contribution:
IBM Bob suggested an explicit, multi-stage state pipeline separating calibration completion from active cursor movement.

Human Team Solution & Integration:
The team implemented an explicit state pipeline: `IDLE` -> `CALIBRATING` -> `CALIBRATION COMPLETE` -> `CURSOR CONTROL READY` -> `[▶ Start Cursor Control]` -> `CURSOR CONTROL ACTIVE` -> `[⏹ Stop Cursor Control]`. Active cursor movement starts **ONLY** when the user clicks **Start Cursor Control**.

--------------------------------------------------
H. VOICE OUTPUT V2.4 SUBMISSION DECISION
--------------------------------------------------
Problem & Decision:
While two-way spoken voice interaction was developed and tested, real-world acoustic feedback during live demonstrations posed a operational risk.

IBM Bob Debugging Contribution:
IBM Bob assisted in analyzing submission stability trade-offs and recommended configuring a dedicated V2.4 Submission Mode.

Human Team Solution & Integration:
The team configured V2.4 Submission Stability Mode (`VOICE_INPUT = ACTIVE`, `VOICE_OUTPUT = DISABLED`, `VISUAL_RESPONSE = ACTIVE`). IRIS processes voice commands and presents responses visually in the UI and Command Log, guaranteeing 100% demo stability while documenting two-way spoken conversation as a FUTURE SCOPE enhancement.
